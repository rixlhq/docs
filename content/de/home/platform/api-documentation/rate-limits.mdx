The API may answer `429 Too Many Requests` when it needs you to slow down, and `503 Service Unavailable` when a backend is overloaded. A `503` from the API carries a `Retry-After` header with the number of seconds to wait. A `429` carries one only when a retry can succeed soon; without it, the limit is a long cooldown and retrying won't help.

## What Your Client Should Do

- Honour `Retry-After` when present, then retry as described in [Retries](/de/home/platform/api-documentation/error-handling#retries).
- Cap concurrency, and batch or cache reads where you can.

<Callout type="warning" title="No published limits">
  RIXL does not publish numeric rate limits. Build for adaptive throttling driven by `Retry-After` rather than fixed numbers.
</Callout>
